# Память при стартовой проверке SHA-256

Проверено 19.10.2026 на Apple M1 / 16 GiB, macOS 27.0.1 (26A434),
Swift 6.4, release `-O`. В исходном отчёте GUI достигал 9,55 GiB physical
footprint на старте. Раздельные опыты подтвердили накопление временных
буферов в общем `Disk.hash`, используемом проверкой моделей и очисткой архива.

## Причина и исправление

`AppModel` сначала вызывает `RecordingCoordinator.recover()`, затем выполняет
`ModelLibrary.load` в `Task.detached`. Проверка профилей читает все модельные
файлы через `Disk.hash`. Восстановление тоже вызывает его, когда перед
удалением временного аудио требуется проверить оригинал.

Хэширование уже читало блоками по 4 MiB, но Foundation-буферы, созданные
`FileHandle.read(upToCount:)`, могли удерживаться внешним autorelease pool
до окончания задачи. В результате размер блока не ограничивал суммарную
память проверки многогигабайтного комплекта.

Теперь каждая итерация чтения **и** `SHA256.update` выполняется внутри
локального `autoreleasepool`; наружу выходит только признак наличия данных.
Исходный дескриптор, последовательность байтов, полный SHA-256, проверка
отмены между блоками и распространение ошибок чтения сохранены. Результат
хэширования и fingerprint не меняются; версия pipeline не изменена.

## Раздельные измерения

Baseline и исправленный probe связаны с release-объектами реального
`LocalScribeCore` до и после изменения. Операции выполняются в отдельных
процессах через `Task.detached`, без параллельной сборки или inference.
RSS и physical footprint снимаются каждые 20 ms; после работы есть 5 секунд
простоя. `maxResidentBytes` из `getrusage` сохраняется отдельно от footprint.

| Операция | Пиковый footprint до, MiB | После, MiB |
| --- | ---: | ---: |
| SHA-256 крупного файла Qwen | 5097,08 | 8,78 |
| `ModelLibrary.load`, исходные четыре профиля / 63 файла | 8704,62 | 9,91–9,99 |
| `RecordingCoordinator.recover`, 1000 записей | 339,64 | 13,72–13,74 |

Проверка моделей и восстановление после исправления повторены в трёх
независимых процессах. Все завершились кодом 0, ошибок сэмплера нет.
Каталог моделей полностью проверял размеры и SHA-256; все четыре профиля
распознаны установленными. В контрольном опыте в исходном probe изменялся
только способ освобождения буферов одного хэширования: SHA совпал,
footprint снизился с 5097,08 до 8,75 MiB.

Модельные файлы подключались только для чтения через симлинки из временной
папки; `selection.json` создавался отдельно в ней. Технический архив
содержал 999 записей метаданных и одну независимую копию синтетического
трёхчасового WAV с временным `work`, чтобы выполнить реальную проверку SHA
перед очисткой. Пользовательский архив не использовался.

Это изолированные процессы стартовых операций, **не повторный замер всей
подписанной GUI `.app`**. Показатель около 10 MiB нельзя выдавать за общий
footprint GUI. Исправление устраняет подтверждённый источник стартового
роста, но не заменяет длительную ресурсную приёмку приложения.

CSV, метки фаз, результаты, исходники диагностического probe и снимки
объектов Core находятся локально в исключённой из Git папке
`TestResults/startup-memory-fix-2026-10-19/`.

## Регрессионная проверка без моделей

[probe_hash_memory.swift](../scripts/probe_hash_memory.swift) хэширует
временный sparse-файл с 256 MiB нулей три раза внутри одного внешнего
autorelease pool. Проверяет известный SHA-256, рост footprint между
вызовами и рост максимального RSS за процесс. Для каждого роста установлен
бюджет 64 MiB; он относится к этому изолированному probe, не к всему GUI.
Максимальный RSS также ловит временный пик внутри одного хэширования.

На прежнем Core probe завершился кодом 1: рост footprint 771,52 MiB.
На исправленном — кодом 0: footprint вырос на 4,16 MiB,
максимальный RSS — на 4,30 MiB. В обоих случаях SHA-256 совпал.
Временный файл удаляется в том числе при превышении бюджета.

Команды из корня пакета; линковка рассчитана на объединённый объект Core
в текущей Xcode/SwiftPM-сборке. Путь к продуктам определяет SwiftPM:

```sh
swift build -c release -j 4 --force-resolved-versions
python3 - <<'PY'
from pathlib import Path
import subprocess

out = Path('TestResults/hash-memory-regression').resolve()
out.mkdir(parents=True, exist_ok=True)
products = Path(subprocess.check_output(
    ['swift', 'build', '-c', 'release', '--show-bin-path'], text=True).strip())
core = products / 'LocalScribeCore.o'
assert core.is_file(), f'Expected merged release Core object: {core}'
probe = out / 'probe'
subprocess.run([
    'xcrun', 'swiftc', '-O', '-swift-version', '6', '-parse-as-library',
    '-target', 'arm64-apple-macos26.0',
    '-module-cache-path', str(out / 'module-cache'), '-I', str(products),
    'scripts/probe_hash_memory.swift', str(core), '-o', str(probe),
], check=True)
subprocess.run([str(probe)], check=True)
PY
```

`DiskHashTests` дополнительно сравнивает файловый SHA с однократным CryptoKit
на пустом, коротком, граничных и многоблочном входах. Отдельно проверяется
хэширование с текущей позиции дескриптора и сохранение владения им.
Проверки отмены, установки/повреждения моделей, импорта и очистки архива
входят в существующий полный набор:

```sh
swift test -c release -j 4 --force-resolved-versions
```

Полный release-прогон: **220 XCTest** (122 Core, 67 UI/service,
31 диаризации), **0 ошибок**, 2 ожидаемых модельных пропуска.

Использованы имеющиеся Metal-артефакты; чистая сборка Metal, упаковка
и подпись `.app` в этой проверке не выполнялись.
