### 1. Пользовательский результат

- Под заголовком **«Записи» в левой панели** расположено постоянно видимое поле поиска. Речь о заголовке списка, а не о названии открытой записи справа.
- При вводе, удалении, вставке и замене текста неподходящие записи скрываются, подходящие остаются. Enter и отдельная кнопка запуска не требуются.
- Поиск работает по `Manifest.displayTitle`, во всех группах, включая свёрнутые. Транскрипция, итоги, имена групп, имена исходных файлов и скрытые метаданные не участвуют.
- Частично введённое слово уже находит название. Например, `вст` находит «Встреча с командой».
- Опечатки в достаточно длинном запросе допускаются: `встеча`, `встрчеа`, `фстреча` находят «Встреча с командой».
- Пустой запрос возвращает обычный список; выбранный результат справа сохраняется при фильтрации.
- Всё работает в памяти, без сети, LLM, обращения к аудио и сканирования архива при вводе.

### 2. Выбранный алгоритм и причины выбора

Используй гибрид: **точное вхождение части слова + ограниченное OSA-сопоставление с префиксом слова**. OSA (Optimal String Alignment) — ограниченный вариант расстояния Дамерау — Левенштейна. Стоимость каждой операции равна 1:

1. Вставка буквы: `встрееча` → `встреча`.
2. Удаление буквы: `встеча` → `встреча`.
3. Замена буквы: `фстреча` → `встреча`.
4. Перестановка двух соседних букв: `встрчеа` → `встреча`.

Обычный Левенштейн считает соседнюю перестановку двумя правками; OSA лучше соответствует такому виду опечаток. OSA проще полного unrestricted Damerau–Levenshtein, но различается с ним на перекрывающихся последовательностях правок. В этой реализации контрактом является именно OSA. Не называть реализацию полным Damerau–Levenshtein. См. [документацию OSA](https://rapidfuzz.github.io/RapidFuzz/Usage/distance/OSA.html) и [Damerau–Levenshtein](https://rapidfuzz.github.io/RapidFuzz/Usage/distance/DamerauLevenshtein.html).

Сравнивать запрос со всем названием по расстоянию нельзя: короткое `встреч` окажется слишком далеко от длинного «Встреча с командой по бюджету». Нужны отдельные слова и бесплатный не введённый ещё хвост слова.

Для первой версии достаточно собственного небольшого Swift-движка без новой зависимости. Подготовленный набор названий сканируется в фоне. Достижение требуемой скорости подтверждается замерами; один выбор алгоритма её не гарантирует.

SQLite FTS5 умеет префиксы, но сам по себе не задаёт нужное исправление опечаток. Его trigram tokenizer также не находит строки короче трёх Unicode-символов через полнотекстовый запрос. Поэтому новый SQL-индекс для этой доработки не нужен. Источник: [SQLite FTS5](https://www.sqlite.org/fts5.html).

Идея ограничивать число опечаток длиной слова используется в поисковых движках: например, у Meilisearch исходные пороги 5 и 9 символов. **Для LocalScribe ниже выбраны собственные пороги 4 и 8**, чтобы допуск работал и в коротких русских словах. Это продуктовая настройка, а не обязательная часть OSA. Источник принципа: [Meilisearch: typo tolerance](https://www.meilisearch.com/blog/typo-tolerance).

### 3. Нормализация и разбиение на слова

Одинаково обрабатывай названия и запрос:

1. Приведи Unicode к совместимой составной форме, например `precomposedStringWithCompatibilityMapping`.
2. Примени case folding с фиксированной локалью `en_US_POSIX`, например `folding(options: [.caseInsensitive], locale: ...)`, чтобы результат не зависел от текущей локали Mac. API: [Apple folding(options:locale:)](https://developer.apple.com/documentation/swift/stringprotocol/folding%28options%3Alocale%3A%29).
3. Явно замени `ё` на `е`.
4. Разбей строку на непрерывные последовательности букв и десятичных цифр. Пробелы, переводы строк, дефисы, подчёркивания, точки, слеши, emoji и прочие знаки — разделители. Комбинируемые знаки внутри буквы сохраняй вместе с её Unicode-графемой.
5. Отбрось пустые токены. Одинаковые нормализованные токены запроса можно убрать, сохранив первый экземпляр.

Не применяй общее удаление диакритики: оно может склеить русские `й` и `и`. В первой версии `й` и `и` различаются, латинские акценты сохраняются. Канонически эквивалентные варианты одной буквы должны совпадать. `ё`/`е` — отдельное явно заданное исключение.

Длину и правки считай по Swift `Character` после нормализации, а не по байтам UTF-8 и не по кодовым единицам UTF-16. Для быстрого доступа один раз готовь массивы графем; не делай `String.index(_:offsetBy:)` во внутренних циклах DP.

Примеры нормализации:

| Вход | Токены |
| --- | --- |
| `  ВСТРЕЧА—по_проекту  ` | `встреча`, `по`, `проекту` |
| `Отчёт / Q4 2026` | `отчет`, `q4`, `2026` |
| `Проект‑Альфа` | `проект`, `альфа` |
| `😀` или `---` | пустой набор |

Если после нормализации токенов нет, фильтр считается пустым и показывает обычный список. Исходный текст поля не изменяется автоматически.

Транслитерация, исправление раскладки, синонимы, морфология, смысловой поиск, склейка/разделение ошибочно написанных слов и специальная сегментация CJK в эту версию не входят. Например, `dcnhtxf` не обязан находить «Встреча».

### 4. Точный контракт совпадения

Пусть `Q` — уникальные токены запроса, `W` — токены названия. Запись подходит, если **каждый** токен из `Q` совпал хотя бы с одним токеном из `W`.

- Между словами запроса используется AND, порядок слов не важен.
- Для каждого токена перебираются все слова названия, а не только первое.
- Один токен названия может удовлетворить нескольким токенам запроса. Это сознательно простой контракт: `проект про` может найти название с единственным словом «Проект».
- Пробел в конце не переключает режим на поиск только полного слова. Это предотвращает скачок выдачи при пробеле.
- Нет ограничения на первые 20/50 результатов: отображаются все совпавшие записи через существующий ленивый список.
- Порядок групп и хронологический порядок внутри группы сохраняются. Ранжирование по сходству не добавляется: пользователь фильтрует существующий список, его строки не должны менять порядок при каждой букве.

Для одного токена `q` и слова `w`:

**Шаг A — точный поиск части слова.** Если `w` содержит `q` подряд в любой позиции, совпадение найдено. Работает с первой буквы, без ошибок. Например, `ект` находит «Проект». Нельзя искать через границу двух слов.

**Шаг B — допуск опечаток у начала слова.** Если A не сработал, вычисли бюджет:

| Длина `q` в графемах | Максимум правок `k` |
| --- | --- |
| 1–3 | 0 |
| 4–7 | 1 |
| 8 и более | 2 |
| Токен содержит хотя бы одну десятичную цифру | 0 независимо от длины |

Цифры и смешанные коды вроде `sprint2026` ищутся только точным вхождением, чтобы исправление не путало даты, номера и версии. Например, `2025` не совпадает с `2026`, но `202` совпадает с `2026` как точная часть.

Если `k == 0`, после неуспешного A совпадения нет. Иначе проверь:

```text
m = число графем q
lo = max(1, m - k)
hi = min(число графем w, m + k)

prefixDistance(q, w) = min OSA(q, prefix(w, j)), где lo <= j <= hi
совпадение, если prefixDistance <= k
если hi < lo, совпадения нет
```

Начало `w` закреплено; хвост после выбранного префикса ничего не стоит. Не требуй точного совпадения первой буквы: `фстреча` должно находить «Встреча». Не разрешай бесплатный пропуск начала `w` в нечётком режиме: это превратит его в гораздо более шумный нечёткий поиск любого фрагмента. Точные внутренние фрагменты уже покрывает шаг A.

Следствие: `встеч` находит «Встреча», хотя слово ещё не введено полностью и одна буква пропущена. Полное слово сравнивать с `q` в данном случае было бы ошибкой.

### 5. Вычисление OSA и ограничения сложности

Для графем `a[1...m] = q` и `b[1...n]`, где `n = min(w.count, m + k)`, используй динамическое программирование:

```text
D[0,j] = j
D[i,0] = i
D[i,j] = min(
    D[i-1,j] + 1,
    D[i,j-1] + 1,
    D[i-1,j-1] + (a[i] == b[j] ? 0 : 1)
)
если i > 1, j > 1, a[i] == b[j-1], a[i-1] == b[j]:
    D[i,j] = min(D[i,j], D[i-2,j-2] + 1)

ответ = min(D[m,j]) для lo <= j <= hi
```

Это не поиск произвольной подстроки: `D[0,j]` равно `j`, а не нулю. Иначе начало слова можно было бы пропускать бесплатно.

Для production вычисляй только полосу `abs(i-j) <= k`, прочие клетки считай `k+1`, значения больше бюджета можно насыщать до `k+1`. Полоса безопасна, потому что путь со стоимостью не выше `k` не может уйти от главной диагонали дальше `k`; соседняя перестановка потребляет два символа с обеих сторон.

Нужны три строки DP, поскольку перестановка обращается к `i-2`. Переиспользуй буферы. Для одной пары слов полоса даёт `O(m * (2k+1))` времени и `O(m+k)` памяти при трёх обычных строках. Это оценка только нечёткого сравнения, без токенизации, точного поиска подстроки, обхода названий и обновления UI.

Без полосы эталонный вариант имеет `O(m * min(w.count, m+k))` времени. Оставь простой полный DP как независимый тестовый oracle, production сверяй с ним на небольших случайных строках и всех бюджетах 0/1/2. Для `k=0` в production достаточно точного шага A.

Дополнительные безопасные отсечения:

- Если `w.count < m-k`, нечёткое совпадение невозможно.
- Не просматривай хвост `w` дальше `m+k` в DP.
- После первого подходящего слова для токена прекращай его перебор.
- После первого неподходящего токена прекращай проверку названия.
- Сначала можно проверять самые ограничивающие токены, например длинные и числовые; AND-семантика сохраняется.
- Проверяй отмену между записями, при работе с длинными токенами — также во внутренних циклах с ограниченным интервалом.

Не добавляй произвольные отсечения по первой букве, одному префиксу, top-K или непроверенному минимуму строки DP: они могут потерять допустимые совпадения. Новые оптимизации должны сохранять результат эталонного алгоритма.

Не используй BK-tree непосредственно с этим расстоянием: OSA не удовлетворяет неравенству треугольника. Пример для OSA между целыми строками: `CA` → `AC` = 1, `AC` → `ABC` = 1, но `CA` → `ABC` = 3. Обычные метрические отсечения BK-tree здесь небезопасны.

Проверяй также отрицательные примеры с заведомо большим расстоянием и отсутствие склейки `про ект` → `проект` как специальной операции. При независимом AND какие-то составные запросы всё же могут совпасть с одним словом через обычные точные фрагменты; это не склейка.

**Важное свойство:** выдача не обязана строго сужаться при добавлении каждого символа. Например, на трёх символах ошибки запрещены, на четырёх включается одна правка. Запись может появиться снова. Поэтому каждый запрос проверяется по полному актуальному набору названий, а не только по результатам прошлого запроса. Возврат назад, замена текста в середине и вставка должны работать точно так же.

### 7. Поле поиска

Размести отдельный `RecordingSearchField` в `RecordingGroupsSidebar`, между HStack с «Записи» и `ScrollViewReader`. Поле остаётся на месте при прокрутке записей.

Внешний вид:

- Placeholder: «Поиск по названиям».
- Высота около 30 pt, горизонтальные внешние отступы 12 pt, нижний отступ около 8 pt. Ширина соответствует доступной ширине панели.
- Скругление около 8 pt, `RoundedRectangle(..., style: .continuous)`, системный фон поля, тонкий системный разделитель/контур. Точные значения допустимо подстроить после проверки реального окна.
- Шрифт системный, примерно 13 pt, текст основной, placeholder и значок вторичного цвета. Системные цвета для светлой/тёмной темы и Increase Contrast.
- **Лупа справа внутри поля**, `Image(systemName: "magnifyingglass")`, примерно 14–15 pt, отступ справа около 9 pt. Прикреплённое пользователем изображение — ориентир тонкого серого значка.
- Лупа видна, только когда исходная строка поля `isEmpty`. Получение фокуса само по себе её не скрывает. Первый введённый символ, включая пробел, скрывает её сразу. Полная очистка возвращает.
- В непустом поле вместо лупы появляется небольшая кнопка очистки `xmark.circle.fill`. Она очищает запрос целиком и оставляет фокус в поле. Это дополнительное удобство, не кнопка запуска поиска.
- Место под правый элемент зарезервировано: текст не наезжает на значок, а при переключении иконок не меняются ширина поля и положение курсора.
- Лупа декоративная, не принимает клики и скрыта от accessibility. Нажатие в поле переводит в него фокус.
- Фокус виден стандартным системным способом либо тонким контуром акцентного цвета, без чрезмерного свечения. Нет крупного стеклянного блока и анимации строк при каждом символе.

Используй `TextField` с `.textFieldStyle(.plain)` внутри оформленного контейнера: это позволяет точно выполнить правое расположение иконки. Стандартный `.searchable` не должен уносить поле в toolbar. Системный поиск Apple обычно использует ведущую лупу; здесь правое расположение — явное требование пользователя. Остальные решения должны сохранять привычные свойства текстового поля. См. [Apple Search](https://developer.apple.com/documentation/swiftui/search) и [Apple: Design intuitive search experiences](https://developer.apple.com/videos/play/wwdc2026/292/).

Клавиатура и доступность:

- Command+F фокусирует поле поиска записей и выделяет имеющийся запрос, когда фокус не находится в редакторе результата/другом текстовом редакторе со своим поиском. Не перехватывай глобально стандартный поиск редактируемого текста.
- Escape при непустом поле очищает его, сохраняя фокус; повторный Escape в пустом поле снимает фокус.
- Enter не нужен для применения запроса и не должен автоматически выбирать/запускать первую запись.
- Не меняй текст, выделение, позицию курсора или marked text при нормализации. Для IME не вмешивайся в композицию: допустимо искать по последнему подтверждённому тексту и применять новый запрос после подтверждения. Обычный RU/EN-ввод обновляет фильтр на каждом изменении.
- VoiceOver label поля: «Поиск по названиям записей»; кнопки очистки: «Очистить поиск». Результаты и сообщение об отсутствии совпадений доступны без озвучивания каждой клавиши отдельным alert.
- Предложенные accessibilityIdentifier: `recordings.search`, `recordings.search.clear`, `recordings.search.empty`, `recordings.search.count`.

### 8. Группы, выбор и действия

Реальное состояние проекта: список уже реализован через группы в `RecordingGroupsSidebar.swift`, с множественным выделением и drag-and-drop. Поиск должен встроиться в эту структуру.

При активном фильтре — то есть при непустом наборе нормализованных токенов:

1. Показывай только группы, содержащие совпавшие записи. Сохраняй их исходный порядок, включая последнее положение «Без темы», когда она видима.
2. Совпавшие записи из сохранённо свёрнутых групп тоже показывай: в поиске группы первоначально раскрыты.
3. Раскрытие в режиме поиска хранится только в памяти. Если пользователь сворачивает группу, меняй временное состояние. При новом нормализованном запросе группы снова раскрываются. «Развернуть все»/«Свернуть все» в поиске управляют только временным раскрытием видимых групп.
4. После очистки восстанавливается обычное сохранённое раскрытие. Ввод, временное раскрытие и очистка не записывают `groups.json`.
5. Счётчик группы показывает `совпало / всего`, например «Работа · 3 / 18». В обычном режиме сохраняется текущий счётчик. Под полем во время поиска можно показать компактное «Найдено: N»; `N` — число совпадений, включая временно свёрнутые группы.
6. Если совпадений нет, показывай под полем сообщение «Записи не найдены» и пояснение «Попробуйте другое название или очистите поиск». Для ещё не завершённого первого поиска это сообщение не показывается.
7. Пустые группы и их обычная подсказка «Перетащите записи сюда…» не выдаются за отсутствие совпадений. При пустом фильтре прежний интерфейс пустых групп сохраняется.
8. Создание/редактирование имени группы остаётся доступным; активный inline-редактор не скрывается фильтром. После сохранения пустая группа может быть скрыта до очистки запроса.

Выбор и безопасность действий:

- Не меняй `AppModel.selection` только потому, что выбранная запись не совпала или её группа временно свёрнута. Открытый результат справа остаётся доступным; автоматического перехода к первому совпадению нет.
- При публикации нового фильтра исключай из `sidebarSelection.ids` записи, скрытые именно текстовым фильтром, и сбрасывай скрытую опору диапазона. Это не должно очищать `selection` и перезагружать открытый результат.
- Если сохранённая primary selection снова проходит фильтр и множественный набор пуст, можно восстановить её одиночную подсветку; прежний скрытый множественный набор автоматически не восстанавливается.
- `sidebarRecordingOrder` должен точно соответствовать реально показанным строкам: только совпадения и только временно раскрытые группы. Shift-диапазон не захватывает скрытые строки; отсутствующая опора даёт обычный одиночный выбор, как сейчас.
- Контекстные групповые действия над строками работают только с текущим набором записей, прошедших фильтр. Не допускай удаления/переноса спрятанных фильтром элементов прежнего выделения. Обычное сворачивание группы сохраняет существующую политику выделения.
- Действия в правой панели относятся к явно открытой записи и сохраняют нынешние проверки/подтверждения.
- `recordings(in:)` остаётся методом полного состава группы: он используется для существующих операций, а не только отображения. Введи отдельные методы/снимок для видимых членов и UI-счётчиков.
- Меню переноса предлагает все допустимые реальные группы, даже если они скрыты поиском. После переноса совпавшая запись появляется в целевой группе с тем же фильтром; исходная пустая группа скрывается.
- Перетаскивание записей и импорт в видимые группы сохраняют существующий контракт. Перестановку самих групп на время поиска отключи: линии между отфильтрованными группами неоднозначно обозначают положение относительно скрытых. Подсказка объясняет, что для перестановки нужно очистить поиск.
- Новый импорт/запись не сбрасывает запрос. Новая запись видна, если название подходит. Явный программный переход может открыть запись справа, даже когда фильтр скрывает её строку.
- Фильтрация не меняет FIFO, обработку, default group, членство, manifests или файлы результатов.

Предлагаемое разделение:

| Часть | Ответственность |
| --- | --- |
| `Sources/LocalScribeCore/RecordingTitleSearch.swift` | Чистая нормализация, токенизация, Sendable-индекс названий и OSA matcher; без AppKit/SwiftUI и I/O |
| `Sources/LocalScribe/RecordingSearch.swift` | `@MainActor ObservableObject`: raw query, поколения запросов, запуск/отмена фоновой работы, публикация результата и временное раскрытие |
| `Sources/LocalScribe/RecordingSearchField.swift` | Ввод, правые иконки, фокус, Escape, accessibility |

| Тесты Core и UI/service | Алгоритм, гонки, группы, выделение, отсутствие I/O и измерения |

У наблюдаемого объекта поиска должен быть явный владелец с устойчивым временем жизни. Sidebar должен непосредственно наблюдать его изменения, если публикации вынесены из AppModel: одно только вложенное свойство `let search` у ObservableObject автоматически не пересылает `objectWillChange`.

Данные движка: минимум `id`, исходный `displayTitle`, подготовленные токены и графемы. Поиск возвращает множество ID, не копии manifests. Видимые строки используют свежие manifests из AppModel, чтобы состояние обработки и прогресс не застывали в поисковом кэше.

Отдели три вида изменений:

1. **Состав/названия:** добавление, удаление, переименование → актуализировать индекс и повторить текущий запрос.
2. **Членство/порядок/раскрытие групп:** перестроить представление из уже найденных ID без повторной нормализации всех названий.
3. **Статус обработки/метр/elapsed:** обновить соответствующий UI без пересоздания поискового индекса.

Название нормализуется один раз при появлении или изменении. Не нормализуй весь архив на каждую букву. Удалённые ID убираются из индекса. Проекция `[id, title]` может сравниваться при очередном опубликованном snapshot, а подготовка изменённых названий выполняется в фоне. Избегай `groupCount * recordingCount` повторных фильтраций/сортировок на каждый render: заранее группируй и сортируй строки в снимке представления и переиспользуй его.

Обработай все реальные пути замены `recordings`, включая восстановление, импорт, переименование и тестовые fixtures; не привязывай обновление поиска только к обработчику клавиатуры или одному UI-действию.

### 10. Фоновое выполнение и защита от гонок

Не вычисляй DP, токенизацию всего архива, сортировку или нормализацию всех названий в `body`/MainActor. Простой `Task { ... }` внутри `@MainActor` сам по себе не выносит CPU-работу с главного актора.

Используй отдельную фоновую задачу с неизменяемым Sendable-снимком и явным handle для отмены, например `Task.detached(priority: .userInitiated)`. Сохраняй проверки Swift concurrency. Допустим эквивалентный отдельный исполнитель с теми же гарантиями.

Правила планирования:

- По умолчанию **без debounce**: нет искусственного ожидания 200–500 мс после последней буквы.
- В каждый момент исполняется не более одной CPU-задачи поиска/построения индекса; ожидает максимум один запрос — самый новый. Новый ввод отменяет текущую задачу через её handle и заменяет pending-запрос. Отменённая работа должна быстро заметить отмену; новая запускается после её завершения.
- Не создавай независимую тяжёлую detached-задачу на каждое нажатие, оставляя старые считать параллельно.
- Для пустого нормализованного запроса показывай готовое обычное представление без ожидания поиска; инвалидируй старый запрос.
- При выключении/закрытии владельца отменяй работу; после shutdown публикаций нет.
- Если индекс ещё строится, сохраняй последний query как pending и ищи по нему сразу после актуализации индекса. Построение не мешает вводить текст.

Каждое задание помечается минимум `(queryGeneration, titleCorpusRevision)`. Перед публикацией на MainActor обе величины должны совпасть с актуальными. Если фон готовит и группировку, добавь ревизию групп/представления либо сгруппируй результат по самой новой версии каталога. Одной проверки текста недостаточно для сценария `а → аб → а`.

Смена только статуса не увеличивает ревизию корпуса названий. Изменение названия/состава увеличивает её и не позволяет прежнему ответу вернуть старое совпадение или удалённый ID.

Отмена через метод actor, занятого синхронным CPU-циклом, недостаточна: этот метод может ждать освобождения actor. Используй отмену handle и `Task.checkCancellation()` непосредственно в вычисляющей задаче. Отменённый/неполный индекс не публикуется.

При наборе допускается оставить предыдущую завершённую выдачу на несколько кадров до новой, без промежуточного пустого списка и потери фокуса. Не публикуй результат уже устаревшего запроса. При удалении записи убирай её строку сразу из актуальных данных независимо от состояния поиска. Если вычисление затянулось более 150 мс, допустима ненавязчивая подпись «Поиск…», но поле и список остаются доступны; не показывай модальную загрузку.

### 11. Требования к отзывчивости и замеры

Проверять в release на доступном Apple Silicon Mac, фиксируя модель Mac, macOS, размер корпуса и условия. Время создания fixtures и первоначального чтения архива не включать в стоимость запроса; первоначальное построение индекса измерять отдельно.

Основной профиль: 10 000 названий, медиана около 40 графем, p95 не более 100, RU/EN/цифры, 1–3 токена запроса общей длиной до 32 графем. Используй также одинаковые префиксы и похожие слова, вызывающие много нечётких проверок, а не только быстрые несовпадения.

Цели после подготовки индекса:

| Метрика | Цель |
| --- | --- |
| Чистый поиск, 1 000 названий | p95 ≤ 10 мс |
| Чистый поиск, 10 000 названий | p95 ≤ 30 мс |
| Последнее изменение ввода → публикация актуального фильтра, 10 000 | p95 ≤ 50 мс, p99 ≤ 100 мс |
| Синхронный блок работы поиска/применения на MainActor | p95 ≤ 4 мс; нет блока > 16 мс в контролируемом прогоне |
| Реакция вычисляющей задачи на отмену | обычно ≤ 5 мс в контролируемом прогоне |
| Архивный I/O при изменении query | 0 |

Это критерии приёмки, не обещание для любого Mac под любой нагрузкой. Приведи фактические цифры; при недостижении целей найди узкое место, не скрывай его увеличением debounce. Время публикации измеряется отдельно от полного показа кадра: визуальную плавность и ввод проверь в реальном окне/через Instruments.

Для серии минимум 200 завершённых запросов после прогрева измерь p50/p95/p99. Отдельно проверь быстрый ввод с интервалами 30–80 мс и вставку/удаление: отменённые запросы не считаются успешно завершёнными быстрыми запросами, измеряется задержка последнего актуального ввода. Отметь длительность первичного индекса, дополнительную память, отсутствие роста при повторных запросах. Названия и запросы не логируй; для отчёта достаточно чисел на синтетических данных.

Проведи отдельный стресс-прогон на 50 000 названий, длинных токенах/вставленном тексте и при работающем worker. Для него не обещается тот же предел 50 мс; обязательны отзывчивое поле, отмена и отсутствие устаревших результатов. Не обрезай молча длинный запрос или название ради прохождения замера.

Если сканирование не укладывается, оптимизируй только после профилирования: повторное использование буферов, кэш совпадений уникальных слов внутри одного запроса, переиспользование подготовленного индекса, затем trie с переносом полосы DP. Не используй заведомо неполный триграммный предфильтр: короткие слова и перестановки могут потеряться. Изменение структуры индекса не должно менять таблицу совпадений.

### 12. Проверки

Добавь содержательные тесты, подтверждающие контракт, а не только внутреннюю структуру реализации.

**Core, например `RecordingTitleSearchTests`:**

- Все положительные/отрицательные примеры из раздела 6.
- Четыре операции, границы длины 3/4 и 7/8, несколько ошибок сверх бюджета.
- OSA `CA/AC = 1`, `CA/ABC = 3`; full-word oracle и prefix matcher проверяются раздельно.
- Случайные маленькие RU/EN-строки: полосатый matcher совпадает с полным DP, включая минимум по допустимым префиксам, для `k=0/1/2`.
- Частичное слово с опечаткой; отсутствие бесплатного пропуска начала; точная внутренняя подстрока; первое слово названия может не подходить, второе — подходить.
- AND, перестановка слов запроса, повторный токен, совпадение двух токенов с одним словом.
- `ё/е`, различие `й/и` на коротких точных запросах, составные Unicode-буквы, разные виды разделителей, ширина символов.
- Числовые/смешанные токены без исправления, пустой и только пунктуационный запрос.
- Названия с одинаковым текстом и разными UUID возвращаются оба; исходный порядок при фильтрации не меняется.

**UI/service, например `RecordingSearchIntegrationTests`:**

- Через fake executor смоделировать доставку устаревшего ответа A после актуального ответа B: показывается B. Отдельно проверить, что production scheduler не исполняет два CPU-поиска одновременно. Проверить также `A → B → A` с разными generation.
- Очистка во время вычисления немедленно возвращает обычный список; старый ответ его не фильтрует снова.
- Переименование/удаление/добавление во время поиска инвалидирует старый корпус; статус обработки не перестраивает токены.
- Поиск находит запись в сохранённо свёрнутой группе; очистка возвращает прежнее раскрытие и не пишет каталог.
- Переход между запросами корректно сбрасывает только временное раскрытие; массовые кнопки работают с временным состоянием.
- Нет совпадений, пустой архив и группы без совпадений показаны разными состояниями.
- Primary selection и открытый результат сохраняются, скрытое множественное выделение исключено из действий; Shift использует только фактически показанный порядок.
- Перенос совпадения между группами обновляет заголовки и счётчики; меню использует актуальное членство, как существующие регрессии.
- Поле остаётся в фокусе при публикации результатов; лупа справа только в raw-empty состоянии; очистка, Escape, accessibility и тёмная тема.
- Нет вызовов чтения manifest/обхода архива/записи индекса от серии изменений query; fixtures создаются во временном UUID-каталоге.

Гонки проверяй управляемыми fake executors/барьерами, а не ненадёжными ожиданиями «sleep и надеяться». Регрессии выделения проверяй по образцам существующих нативных mouse-down/context-menu тестов. Ручная проверка настоящего поля остаётся необходимой.

Уточни фактические имена новых тестовых классов перед запуском. Не заявляй прохождение по команде, которая не нашла ни одного теста. Используй реальные runtime/toolchain и разрешённый доступ к SwiftPM-кэшам. Python/аудиокодеки и модельные прогоны к этой задаче не относятся, если соответствующий код не менялся.

Проверь ширину sidebar 240 pt и увеличенную ширину, светлую/тёмную тему и VoiceOver. Если .app не собиралась/не запускалась, укажи, что нативная визуальная проверка не проведена.

### 13. Границы изменения и определение готовности

Для этой доработки не требуется менять схему хранения, entitlements, Info.plist, подпись, зависимости, каталог моделей, worker, pipelineVersion, fingerprint и форматы результатов. Поисковый индекс и текст запроса живут только в памяти; новый файл архива не создаётся.

Готово, когда:

1. Поле находится под «Записи», имеет скругления и требуемую правую лупу, которая исчезает при вводе.
2. Фильтрация работает без Enter, по всем группам, с частями слов и заданными опечатками.
3. Сохранены данные, очередь, открытый результат, групповые действия и правила выделения; поиск не вызывает архивного I/O.
4. Результаты отменённых/устаревших задач не возвращаются; индекс обновляется при изменении названий.
5. Проверены корректность алгоритма и интеграция, приведены реальные замеры отзывчивости и пределы проверки.
6. В финальном отчёте перечислены изменённые файлы, тесты, p95/p99 и незавершённые ручные проверки. Исторические цифры XCTest из документов не выдаются за текущий прогон.

### 14. Источники и статус решений

Исследование опирается на первичные источники; предлагаемые пороги, UI-размеры, поведение групп и цели задержки являются решениями этой спецификации, а не требованиями библиотек:

- [RapidFuzz OSA](https://rapidfuzz.github.io/RapidFuzz/Usage/distance/OSA.html) — отдельный вариант расстояния, cutoff и ограничения; [исходный код OSA](https://rapidfuzz.github.io/rapidfuzz-cpp/OSA__impl_8hpp_source.html) — технический пример оптимизированного расчёта, не зависимость проекта.
- [RapidFuzz Damerau–Levenshtein](https://rapidfuzz.github.io/RapidFuzz/Usage/distance/DamerauLevenshtein.html) — отличие полного расстояния от выбранного OSA.
- [Meilisearch typo tolerance](https://www.meilisearch.com/blog/typo-tolerance) — принцип порогов по длине и управления допуском; собственная реализация LocalScribe не воспроизводит все правила Meilisearch.
- [SQLite FTS5](https://www.sqlite.org/fts5.html) — префиксный и trigram-поиск, ограничения коротких подстрок.
- [Apple SwiftUI Search](https://developer.apple.com/documentation/swiftui/search) и [Design intuitive search experiences, WWDC26](https://developer.apple.com/videos/play/wwdc2026/292/) — поведение поиска и элементов поля. Правое положение лупы задаёт пользователь.
- [Apple Unicode folding](https://developer.apple.com/documentation/swift/stringprotocol/folding%28options%3Alocale%3A%29) — API нормализации регистра.

При подготовке спецификации изучен текущий код списка, групп, выбора и публикации snapshot. Примеры одиночных опечаток и двух правок проверены отдельным эталонным полным OSA-расчётом. Дополнительно описанная полосатая рекуррентная схема с тремя строками и минимумом по префиксам сверена с полным DP на 11 532 комбинациях строк из двух букв длиной 1–5 и бюджетов 0/1/2: расхождений нет. Это проверка алгоритмического рецепта отдельным Python-прототипом; Swift-реализация, бенчмарки приложения и визуальная приёмка поиска пока отсутствуют.
