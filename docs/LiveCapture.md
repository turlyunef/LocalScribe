# Распознавание во время записи

Чекбокс «Распознавать во время записи» находится в окне настроек над разделом «Этот Mac» и применяется к следующей записи. По умолчанию он включён; сохранённый выбор пользователя сохраняется после перезапуска. Во время записи, её запуска и сохранения чекбокс недоступен. Для старта вместе с микрофоном нужны установленные модели. Выбор профилей фиксируется при создании задания. При занятом worker новая запись ждёт своей очереди: текущая обработка и уже ожидающие задания завершаются первыми. Выключенный чекбокс сохраняет обработку после остановки, но новая запись больше не прерывает старый анализ.

## Поток и состояния

Ожидающие задания получают номера от 1 в порядке фактического запуска; текущий анализ в нумерацию не входит. Кнопка «Поднять на верх очереди» переносит выбранное ожидающее задание на первое место без прерывания текущего worker. Это относится и к фоновому распознаванию ещё записываемого микрофона. Остальные задания сохраняют взаимный порядок; новая запись по умолчанию добавляется в конец очереди.

GUI по-прежнему владеет manifest, а единственный последовательный worker пишет результаты в runs. `Manifest.state = recording` описывает микрофон; необязательное `captureProcessing` отдельно описывает очередь, распознавание, его ошибку или приостановку. Ошибка модели не меняет владельца микрофона и не останавливает запись. После остановки обычные состояния этапов снова описывают обработку завершённого исходника. Старые manifests и команды без новых необязательных полей продолжают декодироваться.

Если при сохранении оригинала worker ещё распознаёт эту запись, её статус переходит в «Распознаём речь», с индикатором и кнопкой отмены. «Сохранено» и «Продолжить» не должны появляться вместо выполняющегося этапа: фоновые окна, включая хвост, завершаются тем же worker без повторного запуска. Если запись ждала другого задания, после сохранения она остаётся в очереди на прежнем месте.

Worker получает одну JSONL v1 команду `transcribing` с `liveCapture = true`, загружает Whisper и наблюдает закрытые CAF на диске. Незавершённые `.partial.caf` не читаются. Очередь звука не копируется в RAM: в память поступают только соседние фрагменты одного окна. Основные интервалы — до 30 секунд, контекст — по секунде с обеих сторон. Внутри остаётся выбор границ у пауз, определение языка и фильтрация Whisper; принадлежность слова задаётся серединой его исходного временного интервала. Готовое окно сохраняется атомарно в `live/part-N.json`. Первое окно может стартовать после закрытия четырёх десятисекундных фрагментов (около 40 секунд звука), плюс время загрузки модели и распознавания. Допускается любое отставание.

При остановке GUI снимает tap и дожидается последовательной writerQueue, закрывая последний короткий CAF. Число сэмплов сверяется с результатом сборки оригинала. Только затем публикуется `capture-seal.json`: новых фрагментов больше не будет. Worker завершает оставшиеся интервалы, включая короткий хвост. Он не запускает диаризацию и итоги до завершения потока.

## Проверка и восстановление

До остановки `capture-run.json` хранит неизменяемый RunInfo с идентификатором сессии вместо ещё неизвестного SHA оригинала. Каждая контрольная точка содержит fingerprint профилей/версии pipeline, границы основного окна и контекста, номера, длины и SHA-256 входных CAF. Повтор использует только совпавшие контрольные точки. Несовпадение не превращается в успешный результат.

Seal связывает эти же фрагменты с SHA-256 завершённого оригинала. Worker и GUI потоково сверяют его PCM со всеми закрытыми фрагментами и проверяют исходные SHA. GUI проверяет непрерывное покрытие окнами, формирует обычный `asr-transcript.json` и RunInfo с окончательным fingerprint. Публикация повторяема после сбоя; контрольные точки не переписываются. Полного повторного ASR после остановки нет. Нормализация всего оригинала остаётся нужна для единственного глобального прохода SpeakerKit; затем создаются итоги.

CAF не удаляются при сборке оригинала фоновой записи. Они остаются до проверенного присоединения ASR и выхода worker. Восстановление после сбоя, ошибки модели или отмены сохраняет вход незавершённого задания; «Продолжить» достраивает исходник/отметку завершения и использует сохранённые окна. Незакрытый фрагмент после аварии по-прежнему может быть утрачен. `activeRunId` переключается только после проверки всех финальных артефактов.

Worker работает с utility QoS; при записи дополнительно понижается приоритет CPU/диска. Warning/critical memory pressure отменяет worker с освобождением моделей, сохраняя его место и остальные задания; normal pressure позволяет продолжить. Заметное заполнение пула микрофона также приостанавливает обработку до остановки записи. Перегрев задерживает новые окна. Callback микрофона не ждёт распознавание и не выполняет файловых операций. Эти меры требуют стресс-проверки на целевом Mac: они не гарантируют отсутствие пропусков при произвольной системной нагрузке.

## Проверки

`swift test -c release -j 4 --force-resolved-versions` проверяет очередь через настоящий supervisor и тестовый процесс: старая работа переживает новую запись, следующая ждёт, ошибка фоновой модели сохраняет `recording`. Контрактные тесты проверяют хвост 125 ms, несовпавшие SHA/PCM, отсутствие окна, fingerprint, повторную публикацию и очистку только после присоединения ASR.

`ProcessingQueueTests` также проверяет сохранение оригинала при работающем ASR: статус остаётся `transcribing`, повторный вызов продолжения не запускает сохранение, тот же run завершается автоматически. Отдельно проверены сохранение ожидающей записи без потери FIFO и действительное продолжение того же run после ошибки worker. До исправления первая проверка воспроизводила `recorded` при работающем worker — источник ошибочной кнопки «Продолжить».

Для сохранённой в очереди записи запуск live ASR переводит основной статус из `queued` в `transcribing`; пока микрофон ещё пишет, обновляется отдельный `captureProcessing`. Регрессия `testSavedQueuedCapturePublishesProcessingStatusWhenItsWorkerStarts` удерживает worker после первого progress и проверяет manifest, статус в списке и тексте результата, отсутствие номера у текущего задания и сдвиг номера ожидающего. До исправления worker уже работал, но запись оставалась «В очереди» в manifest и UI.

Проверено 19.10.2026: `swift test -c release -j 4 --force-resolved-versions --filter 'ProcessingQueueTests|ResultPresentationTests'` — 27 тестов, 0 ошибок.

После исправления статуса 18.10.2026 полный release-прогон XCTest прошёл без ошибок: 71 Core + 41 UI/координатор, включая 6 тестов очереди. Установленная `.app` этой проверкой не обновляется.

`python3 scripts/probe_live_capture.py` — явный технический прогон с локальными `Assets/probe/mixed.wav`, `Assets/probe-models` и `Assets/tools`, после сборки worker. Путь executable определяется через SwiftPM. Прогон создаёт только синтетические данные в исключённом из Git `TestResults/live-capture-*`, получает первую контрольную точку до остановки, закрывает stdin, дописывает хвост 125 ms и возобновляет worker. Проверяются неизменность первой контрольной точки и конец последнего окна 40 125 ms. SDK stderr разрешён только в этой технической папке; приложение его не сохраняет. Пользовательский архив не используется.

Остаются ручные проверки TCC/микрофона, реальной нагрузки и memory pressure, сна, аварийного завершения GUI и длинных встреч, а также оценка слов на стыках и WER/DER по эталону. Техническая синтетическая речь не заменяет эти проверки.

Проверено 18.10.2026: release-сборка и 102 XCTest (68 Core + 34 UI/координатор), без ошибок. Настоящий локальный Whisper получил контрольную точку при незавершённом исходнике, завершился по EOF с кодом 72 и продолжил после публикации seal; SHA первой контрольной точки не изменился, последний интервал завершился на 40 125 ms. Тумблер отдельно отрисован в светлой и тёмной теме. Использованы имеющиеся Metal-артефакты; чистая сборка без установленного Metal Toolchain не подтверждается.
