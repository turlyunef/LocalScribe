# Что писать в AGENTS.md

Все примеры ниже иллюстративные. Не переносить имена, команды и запреты в
документ без подтверждения в целевом проекте. Если данных нет, опусти раздел
или кратко укажи конкретную неизвестность, мешающую работе.

| Секция | Содержание | Хорошая формулировка | Плохая формулировка |
| --- | --- | --- | --- |
| Обзор | 2–4 строки о назначении и существенных ограничениях платформ/toolchain | «CLI также собирается в Linux CI; UI-модуль собирается только на macOS. Версия Xcode закреплена в [.xcode-version](.xcode-version).» | «Это современное Swift-приложение.» |
| Структура | Только папки/модули, чьи роли нужны для изменения | «[Core](Sources/Core/) не импортирует UI: его тестирует Linux job.» | Полный вывод tree без объяснений. |
| Команды | Точный cwd, build, один/все тесты, lint/format/generate, статус каждой | «Из корня: `swift test --filter ParserTests/testEmpty` — проверено, выполнен 1 тест.» | «Запусти тесты», `xcodebuild -scheme YourApp`. |
| Архитектура | Подтверждённые границы и файл-образец | «Зависимости экрана передаются через init; образец — [DetailFeature](Sources/DetailFeature.swift).» | «Используем Clean Architecture», выведенное из папки Models. |
| Конвенции | Только нетривиальные локальные правила | «Ошибки API переводятся в DomainError в [APIClient](Sources/APIClient.swift): UI не зависит от транспортных кодов.» | «Пиши чистый код и следуй SOLID.» |
| Тестирование | Фреймворки, naming, mock/fixtures, важные сценарии по фактам | «Для репозиториев используй in-memory fake из [TestStore](Tests/Support/TestStore.swift), чтобы тесты не меняли локальную БД.» | «Стремись к 100% coverage», если проект этого не требует. |
| Границы | Всегда / спроси сначала / никогда, с причиной | «Никогда не редактируй generated API: генератор перезапишет его; меняй schema.» | «НИКОГДА не трогай конфиги», без области и причины. |
| Зависимости | Manifest, lockfile, способ pin/update и подтверждённые причины | «Package.resolved отслеживается; при разрешённом обновлении приложи изменения lockfile.» | «Package.resolved никогда не коммитится» для любого Swift-проекта. |
| Git и PR | Реальные правила либо осторожное описание практики | «В последних коммитах преобладает `fix:`; обязательный формат в CONTRIBUTING не задан.» | «Всегда заводи feature/*», потому что найдена одна такая ветка. |
| Ловушки | Причина, симптом, подтверждённое решение | «Snapshot suite требует локаль en_US из CI: иначе меняется формат даты.» | «Тесты иногда нестабильны», без свидетельства. |

## Команды

Одна строка таблицы — одна точная запускаемая команда. Для Xcode не опускай
project/workspace, scheme, destination; укажи cwd и нужную конфигурацию. Из CI
разреши ссылки на variables/matrix только при известном значении. Секретные
значения не подставляй, а пометь зависимость от секрета и `(не проверено)`.
В документах на других языках сохраняй буквальный маркер `(не проверено)`,
чтобы непроверенные команды легко находились; причину пиши на языке документа.

Если найдена команда, но она упала, не называй её проверенной рабочей командой.
Сохрани факт `запущено, ошибка`, источник и диагноз; задачу исправления сборки
не начинай автоматически. Отсутствующие lint/format/generate не заменяй
модными инструментами. Для изменяющих файлы команд укажи это свойство.

## Три уровня границ

- **Всегда:** доказанные необходимые действия и причина (например, генерация
  клиента после изменения schema, чтобы код соответствовал контракту).
- **Спроси сначала:** действие, для которого нет явного поручения или не хватает
  существенного решения (например, изменение entitlements затрагивает права приложения).
  Уже полученное явное поручение не требует повторного подтверждения.
- **Никогда:** запрет в определённой области с причиной и допустимым способом работы
  (например, не редактировать производный файл; менять исходник генератора).

Если специальных границ нет, используй только установленные этой задачей
инварианты: следовать применимым вложенным инструкциям, уточнять намеренное
изменение документированных правил, не выдавать незапущенные команды за проверенные.
Не выдумывай проектную политику, чтобы заполнить три строки.

## Лимит и сохранение авторского текста

Цель — обычно 70–120 строк, жёсткий предел корневого файла — 150. Сокращай
повторения, а не факты. Подробные инструкции помещай в docs/agents/, например:
«Перед изменением persistence читай [миграции](docs/agents/migrations.md)».
Обзор, основные команды и границы должны быть видны в корне.

Для ручного файла сохраняй существующий порядок и дополнительные авторские
разделы. Правка устаревшей команды должна иметь новый источник. При конфликте
ручного правила и наблюдаемой практики не удаляй правило молча: опиши расхождение.
Перенос длинного авторского раздела должен сохранять весь текст и рабочие ссылки;
показывай в diff как корневой документ, так и создаваемый файл с подробностями.
